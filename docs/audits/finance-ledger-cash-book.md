# Finance and Ledger Audit: Cash Book

## Scope

Cash Book, Bank Book, Expense Entry, Day Book, Cash Register, POS payment posting, transaction numbering, and day-close persistence were traced from UI actions through controllers, repositories, and SQLite tables. This review covers source behavior and automated tests; it does not certify the contents of any production database.

## Corrected findings

| Severity | Finding | Resolution |
| --- | --- | --- |
| Critical | Cash Book's bill sync used the full paid amount, including UPI/card and later collections, to create cash receipts. | Reconciliation now uses the bill's cash payment snapshot, runs atomically, and retires inflated legacy cash receipts when the bill split proves the amount wrong. |
| Critical | A day-close flag lived only in local preferences, leaving the ledger writable. | Database-backed day closures and SQLite triggers block changes to closed cash movements and bank financial fields. Existing preference locks migrate at startup. Later bank statement reconciliation remains possible. |
| High | Cash Book and Day Book balances included noncash entries and omitted prior cash movement from the opening balance. | Cash-only filters, carried-forward movement, and SQL aggregate summaries now determine the cash balance. |
| High | Day Book treated an old bill's unsplit paid amount as cash even when its payment method was unknown. | Unknown legacy payments remain unallocated until a payment split or ledger receipt establishes their mode. |
| High | Noncash Expense Entry had no linked Bank Book debit. | An active account is required; expense source and bank debit are created and voided in one transaction. |
| High | Source-generated receipts could be voided through Cash Book/Bank Book actions. | Manual voids require a reason; generated rows are blocked. The bank UI reports the actual write result. |
| High | POS silently wrote UPI/card payments to the cash transaction table when no bank account existed. | Checkout now requires an active bank account for UPI/card and posts those payments to Bank Book. |
| Medium | Finance transaction numbers were generated by separate methods and could race with inserts. | Cash, expense, and manual bank ID generation now uses the shared numbering service inside write transactions. |
| Medium | Cash Book summary loaded every selected transaction into Dart memory. | Category totals and counts are now aggregated in SQLite. |

## Remaining risks

| Severity | Risk | Required follow-up |
| --- | --- | --- |
| High | Historical bank receipts with a generic bill reference and an amount that conflicts with the bill's UPI/card split cannot be safely assigned to a payment mode or account automatically. | Review those records against bank statements, then post a supervised correction. Reconciliation raises an error instead of duplicating money. |
| High | Some older Expense and Day Book read helpers still turn database errors into empty or zero results. | Propagate failures through their controllers and render an explicit unavailable state, with focused failure tests. |
| Medium | The existing POS checkout repository and central database class remain large and contain multiple concerns. | Extract bounded services in separate, tested changes. A broad rename or split during the cash-ledger correction would put unrelated checkout and migration flows at risk. |
| Medium | Existing financial columns use SQLite `REAL` values. | Move monetary storage to integer minor units or a decimal representation through a separately audited migration across all affected modules. |

## Verification

- Finance ledger regression tests cover cash carry-forward, split-payment reconciliation, legacy cash correction, linked expense reversal, and closed-day writes.
- Legacy database migration tests, the full Flutter test suite, static analysis, and a Windows release build are the release gates for this change.
